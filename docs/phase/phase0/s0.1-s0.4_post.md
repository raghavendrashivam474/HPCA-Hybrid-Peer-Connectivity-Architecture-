### 2.2 Sprint S0.2 — Research Matrix

**Objective:** Study existing peer connectivity systems before designing HPCA abstractions.

**What was implemented:**
- Produced `docs/research/research.md` documenting the central research question, primary and secondary reference systems, and a structured 11-question evaluation framework.
- Executed detailed investigations of all five primary systems: **libp2p, WebRTC, QUIC, WireGuard/Tailscale, Bluetooth (BLE & RFCOMM)**.
- Captured secondary systems (**Matrix, Signal, ZeroMQ, NATS**) with focused BORROW/AVOID observations.
- Produced a consolidated **Comparative Research Matrix** table summarizing each system's problem, abstraction, benefit, cost, and HPCA-specific decision.
- Recorded the architectural synthesis under three clean headings: **BORROW, AVOID, and EXPERIMENT.**
- Documented known unknowns with concrete investigation plans (e.g., BLE advertisement payload size limits, cellular+Wi-Fi parallel probe overhead).

**Key research outcomes:**
- **BORROW:** Identity decoupling (libp2p, WireGuard), path-agnostic ConnectionId (QUIC), parallel reachability probing (WebRTC ICE), stateless roaming endpoint updates (WireGuard), and beacon-only discovery (BLE/mDNS).
- **AVOID:** Dynamic string multiaddrs, multistream-select round-trips, UDP-exclusive transport, kernel TUN/TAP dependencies, and over-nested abstraction layers.
- **EXPERIMENT:** 32-byte cryptographic PeerIds, typed candidate address enums, lightweight binary probe protocol, and minimal session token continuity across transport rebinds.

### 2.3 Sprint S0.3 — Architecture Vocabulary

**Objective:** Turn research into precise, authoritative terminology before designing APIs.

**What was implemented:**
- Produced `docs/architecture/vocabulary.md` defining **eleven core concepts** across three groupings:
  - *Identity & Location:* `Peer`, `PeerId`, `Address`, `Endpoint`
  - *Connectivity & Transport:* `Discovery`, `Reachability`, `Path`, `Transport`
  - *Session & State:* `Connection`, `ConnectionId`, `Session`
- Each term follows a consistent structural template: **Definition → Represents → Does NOT Represent → Relationships → Why HPCA Needs It.**
- Documented seven **Critical Architectural Distinctions** as strict non-equivalence rules:
  ```
  Peer ≠ PeerId
  PeerId ≠ Address
  Address ≠ Endpoint
  Endpoint ≠ Reachability
  Reachability ≠ Connection
  Connection ≠ Session
  Transport ≠ Path
  ```
- Explicitly warned Phase 1 developers not to prematurely create Rust structs from these definitions before each sprint permits it.

**Value delivered:** All Phase 1 API decisions can now be validated against this vocabulary. Any conflation of these concepts in code will be caught during review.

## 3. Problems Encountered & Mitigations

### Problem 1: Accidental Scaffolding Inside the Wrong Repository
- **Issue:** The initial Block 1 PowerShell script defaulted to `$HOME\Projects\HPCA`, but was executed while the terminal's working directory was inside `aryntra-pravah/`. This caused empty HPCA directory structures to be created *inside* the Pravah repository, and `git init` was run against the already-initialized Pravah `.git` directory (reporting *"Reinitialized existing Git repository"*).
- **Risk assessed:** Zero — no Pravah source files were modified or removed; only empty directories were created, and `git init` on an existing repository is idempotent for tracked history.
- **Mitigation applied:**
  1. Detected the misplacement immediately from the tree output showing Pravah's Java package structure alongside the new folders.
  2. Wrote a targeted cleanup script that removed only the newly-created empty folders (guarded by an emptiness check to prevent any accidental deletion of Pravah content).
  3. Verified Pravah's `git status` was clean post-cleanup (no tracked files touched).
  4. Rebuilt HPCA in its correct, sibling location: `C:\Users\ragha\Documents\Anti-grav\HPCA\`.
- **Preventive lesson learned:** Future scripts will explicitly bind `$root` to an absolute intended path and print/confirm it *before* any directory or Git operation runs.

### Problem 2: Cross-Platform Line-Ending Warnings from Git
- **Issue:** Git repeatedly emitted `warning: LF will be replaced by CRLF the next time Git touches it` on Windows during commits.
- **Assessment:** These are benign advisory warnings due to Windows filesystem defaults. No file content was corrupted, and no commit was blocked.
- **Mitigation:** Acknowledged as expected on Windows dev environments. If the wider team standardizes on cross-platform contribution, we can later add a `.gitattributes` file enforcing consistent line endings — deferred as an ADR-worthy decision, not an urgent fix.

### Problem 3: Temptation to Prematurely Create Multi-Crate Workspaces
- **Issue:** The directory structure (`core/`, `protocol/`, `transport/`, etc.) invited immediate creation of separate `hpca-core`, `hpca-transport`, etc. Cargo crates.
- **Mitigation applied:** Explicitly deferred multi-crate architecture per the brief's rule: *"Directories may represent future boundaries; crates should represent actual current boundaries."* HPCA currently ships as a single minimal crate. Multi-crate splitting will be triggered only when a demonstrated compilation-boundary requirement emerges during Phase 1 or later. This decision is captured architecturally in `docs/architecture/architecture.md` under **Architectural Policies**.

### Problem 4: Risk of Speculative Abstractions During Vocabulary Definition
- **Issue:** During S0.3, defining eleven precise concepts naturally suggested writing corresponding Rust structs (`Peer`, `Endpoint`, `Path`, etc.) immediately.
- **Mitigation applied:** Enforced the brief's guardrail — vocabulary was documented as prose definitions and non-equivalence rules only. No Rust types were created. Implementation is strictly deferred to Phase 1, one sprint per concept, with tests validating each type against its definition.

## 8. Recommendation & Next Steps

Phase 0 has produced a research-backed, minimally-scoped architectural candidate ready for empirical validation. I recommend proceeding to **Phase 1 — Core Connectivity Model**, beginning with **S1.1: Peer Identity**.

**Proposed Phase 1 sprint sequence:**
1. **S1.1 — Peer Identity:** Implement the 32-byte cryptographic `PeerId` type, generation, byte-level serialization, and human-readable (Base58 or Hex) encoding with roundtrip tests.
2. **S1.2 — Candidate Addressing:** Implement strongly-typed multi-transport `CandidateAddress` enum covering IPv4/IPv6/SocketAddr and (behind feature flag) Bluetooth MAC.
3. **S1.3 — Reachability Probing:** Implement the binary probe challenge/response state machine and unit-test its lifecycle transitions.
4. **S1.4 — Transport Trait + Loopback Driver:** Define the minimal `Transport` trait and provide an in-memory loopback implementation to satisfy an integration test that exercises the full Peer → Address → Probe → Transport → Session flow.

Each Phase 1 sprint will be committed in the same capability-scoped, small-block discipline used in Phase 0. Any architectural surprise discovered during implementation will trigger an ADR before code changes, per the discipline established here.

Pravah continues independently and remains unaffected by this work.
