## 3. Sprint-by-Sprint Implementation

### 3.1 S1.1 — Peer Identity

#### What Was Implemented
- **File:** `src/core/peer_id.rs`
- **Public API:**
  - `PeerId` (struct wrapping `[u8; 32]`)
  - `PeerIdError` enum (`InvalidLength`, `InvalidHex`)
  - `PEER_ID_LENGTH = 32` constant
- **Capabilities:**
  - `PeerId::random()` — cryptographic identity generation
  - `PeerId::from_bytes`, `to_bytes`, `as_bytes`, `TryFrom<&[u8]>` — byte-level operations
  - `PeerId::to_hex`, `from_hex`, `Display`, `Debug`, `FromStr` — human-readable encoding
- **ADR:** [ADR-0002 — Peer Identity Cryptographic Primitive and Encoding](docs/decisions/ADR-0002-peer-identity-primitive.md)

#### How
Per Section 4 of the brief, the cryptographic mechanism required explicit validation. Phase 0 vocabulary explicitly referenced *"Ed25519 public key or cryptographic hash thereof"* as the identity primitive. ADR-0002 formalized this: **Ed25519 verifying key (32 bytes) generated via `ed25519_dalek::SigningKey::generate(&mut OsRng)`**. The public key is the identity; the private key is discarded at generation time in S1.1 (signature use is deferred to later phases).

Encoding was chosen as **lowercase hexadecimal (64 characters)** over Base58. The rationale: hex has a strict length invariant (64 chars ↔ 32 bytes always), is unambiguous, is universally supported for debugging, and requires only the tiny `hex` crate. Base58 would have added encoding ambiguity and diagnostic friction without benefit at this stage.

#### Testing
Seven tests covering:
- Exact 32-byte size (`std::mem::size_of`)
- Generation uniqueness across multiple calls
- Byte round-trip via `to_bytes` / `from_bytes` / `TryFrom<&[u8]>`
- Hex round-trip via `to_hex` / `from_hex` / `FromStr`
- Invalid byte slice rejection (31 and 33 bytes)
- Invalid hex rejection (short + invalid characters)
- Display/Debug format correctness

#### Problems Faced & Mitigation

**Problem 1: Wrong `FromStr` associated type name.**
Initial implementation used `type Error = PeerIdError` on the `FromStr` impl, but `std::str::FromStr` defines the associated type as `Err`, not `Error`.
```
error[E0437]: type `Error` is not a member of trait `FromStr`
```
**Mitigation:** Surgical rename to `type Err = PeerIdError` and `Self::Err` in the return signature. Root-cause diagnosis before applying any fix.

**Problem 2: Ambiguous `AsRef` dispatch in tests.**
`PeerId` implements both `AsRef<[u8]>` and `AsRef<[u8; 32]>`. A test line `peer_id.as_ref().len()` produced:
```
error[E0282]: type annotations needed
```
because both `&[u8]` and `&[u8; 32]` have `.len()`.
**Mitigation:** Explicit typed bindings in the test:
```rust
let slice: &[u8] = peer_id.as_ref();
let array_ref: &[u8; 32] = peer_id.as_ref();
```
This is architecturally correct: both trait implementations should be exercised.

**Problem 3: Dead code smell in test.**
An early test had a bizarre `from_from_from_str` helper that added unnecessary indirection.
**Mitigation:** Removed the helper, simplified to a direct `assert_eq!(original, from_str_parsed)`.

**Problem 4: rustfmt line-length wrapping.**
Four expressions exceeded the default line length.
**Mitigation:** `cargo fmt` auto-applied, no manual edits.

### 3.2 S1.2 — Candidate Addressing

#### What Was Implemented
- **Files:** `src/core/address.rs`, `src/core/mod.rs`
- **Public API:**
  - `CandidateAddress` enum (`Ipv4(SocketAddrV4)`, `Ipv6(SocketAddrV6)`, `Memory(u64)`, `Bluetooth([u8; 6])` behind `cfg(feature = "bluetooth")`)
  - `AddressError` enum (`UnexpectedEndOfBuffer`, `UnknownAddressType`, `InvalidTextRepresentation`, `InvalidLength`)
- **Capabilities:**
  - Constructors: `from_ipv4`, `from_ipv6`, `from_socket_addr`
  - Accessors: `as_socket_addr` (returns `Option`)
  - Binary encoding: `to_bytes` / `from_bytes` with tag discriminators
  - Text encoding: `Display` / `FromStr` with typed prefixes (`ipv4:`, `ipv6:`, `memory:`) and plain `SocketAddr` fallback
  - Conversions: `From<SocketAddr>`, `From<SocketAddrV4>`, `From<SocketAddrV6>`
- **ADR:** [ADR-0003 — Strongly Typed Candidate Addressing](docs/decisions/ADR-0003-candidate-addressing.md)

#### How
Per Section 5, the implementation strictly enforces `Address ≠ Endpoint ≠ Reachability`. `CandidateAddress` contains **no socket descriptors, no connection state, and no reachability information**. It is a pure location descriptor.

The `Memory(u64)` variant was introduced anticipating the S1.4 loopback transport; adding it here rather than in S1.4 kept the address model complete and closed. This aligned with the brief's requirement to avoid special-casing the loopback driver.

Binary wire format uses single-byte type tags:
| Variant | Tag | Payload | Total |
|---|---|---|---|
| IPv4 | `0x01` | 4-byte IP + 2-byte port | 7 bytes |
| IPv6 | `0x02` | 16-byte IP + 2-byte port | 19 bytes |
| Memory | `0x03` | 8-byte u64 (big-endian) | 9 bytes |
| Bluetooth | `0x04` | 6-byte MAC | 7 bytes |

#### Testing
Six tests covering:
- IPv4 round-trip (binary + text + plain `SocketAddr` fallback)
- IPv6 round-trip (binary + text + plain `SocketAddr` fallback)
- Memory round-trip (binary + text)
- `SocketAddr` bidirectional conversion (including `as_socket_addr()` returning `None` for non-network variants)
- Invalid binary buffer rejection (empty, unknown tag, short payload)
- Invalid text parsing rejection (bad prefix, malformed IP, non-numeric memory ID)

Plus S1.1 tests (7) remained green — regression discipline satisfied.

#### Problems Faced & Mitigation

**Problem 1: Undeclared `bluetooth` feature triggered `check-cfg` under `-D warnings`.**
Modern Rust (`check-cfg` on by default) requires every `#[cfg(feature = "...")]` to be declared in `Cargo.toml`:
```
error: unexpected `cfg` condition value: `bluetooth`
```
Six such errors from six `cfg` sites.
**Mitigation:** Added a `[features]` section to `Cargo.toml`:
```toml
[features]
default = []
bluetooth = []
```
Also switched to `cargo clippy --all-targets --all-features -- -D warnings` to ensure the feature-gated code path itself is linted going forward.

### 3.3 S1.3 — Reachability Probing

#### What Was Implemented
- **Files:** `src/protocol/probe.rs`, `src/protocol/mod.rs`
- **Public API:**
  - `ProbeRequest` (nonce + target peer ID)
  - `ProbeResponse` (nonce + responder peer ID)
  - `ProbeState` enum (`Created`, `AwaitingResponse`, `Succeeded(Duration)`, `Failed(ProbeError)`)
  - `ProbeStateMachine` (owns request, state, sent timestamp)
  - `ProbeError` enum (`InvalidFrameLength`, `UnknownTag`, `ChallengeMismatch`, `PeerIdMismatch`, `InvalidStateTransition`)
  - Constants: `NONCE_LENGTH = 16`, `PROBE_FRAME_LENGTH = 49`
- **ADR:** [ADR-0004 — Lightweight Binary Reachability Probing](docs/decisions/ADR-0004-reachability-probing.md)

#### How
Per Section 6 of the brief, the design is deliberately minimal. Wire format:

```
ProbeRequest  = [0x01 (1)] + [Nonce (16)] + [TargetPeerId (32)]  = 49 bytes
ProbeResponse = [0x02 (1)] + [Nonce (16)] + [ResponderPeerId (32)] = 49 bytes
```

The nonce is a 16-byte cryptographically random challenge (`rand::thread_rng().fill_bytes`). The responder must echo the exact nonce **and** assert its own `PeerId`. The initiator's state machine rejects any response where:
- The frame length is not 49 bytes
- The tag byte is not `0x02`
- The nonce does not match the outbound request's nonce
- The responder identity does not match the target identity

State transitions are enforced defensively:
```
Created --on_sent()--> AwaitingResponse --handle_response()--> Succeeded(rtt) | Failed(err)
```
Attempting to call `handle_response` before `on_sent` returns `InvalidStateTransition`.

RTT is measured via `std::time::Instant` captured at `on_sent` and elapsed at successful response.

#### Testing
Five tests covering:
- Frame round-trip (both `ProbeRequest` and `ProbeResponse` byte encoding)
- Successful state machine flow with RTT measurement
- Rejection of mismatched challenge nonce (transitions to `Failed`)
- Rejection of impostor responder (correct nonce but wrong peer ID)
- Rejection of invalid frames (short buffers and unknown tags for both request and response types)

Plus S1.1 (7) and S1.2 (6) tests remained green.

#### Problems Faced & Mitigation

**Problem 1: Unused variable under `-D warnings`.**
The initial round-trip test declared `let peer_a = PeerId::random();` but never used it.
```
error: unused variable: `peer_a`
```
**Mitigation:** Removed the dead variable. The test uses a single `peer_target` for both request creation and response construction, which is what the semantics actually required.

### 3.4 S1.4 — Transport Trait, Loopback Driver, and Session

#### What Was Implemented
- **Files:** `src/transport/mod.rs`, `src/session/mod.rs`, `tests/integration_test.rs`
- **Public API:**
  - `Connection` trait (`Send + Sync`): `send`, `recv`, `local_addr`, `remote_addr`
  - `Transport` trait: `listen`, `dial`, `accept`
  - `LoopbackTransport` (concrete driver)
  - `LoopbackConnection` (concrete connection)
  - `TransportError` enum (`AddressInUse`, `Unreachable`, `ConnectionReset`)
  - `Session` (stable `session_id`, local/remote peer identities, wrapped connection)
- **ADR:** [ADR-0005 — Transport Abstraction, Loopback Driver, and Session Layers](docs/decisions/ADR-0005-transport-loopback-session.md)

#### How
Per Section 7 of the brief, the transport abstraction is derived from the actual Phase 1 flow, not designed as a universal networking framework.

The trait surface is intentionally narrow:
```rust
pub trait Connection: Send + Sync {
    fn send(&self, data: &[u8]) -> Result<(), TransportError>;
    fn recv(&self) -> Result<Vec<u8>, TransportError>;
    fn local_addr(&self) -> CandidateAddress;
    fn remote_addr(&self) -> CandidateAddress;
}

pub trait Transport {
    fn listen(&mut self, local: CandidateAddress) -> Result<(), TransportError>;
    fn dial(&mut self, peer_id: PeerId, remote: CandidateAddress)
        -> Result<Box<dyn Connection>, TransportError>;
    fn accept(&mut self) -> Result<Box<dyn Connection>, TransportError>;
}
```

The `LoopbackTransport` driver uses:
- A **process-global `LOOPBACK_SWITCH`** (a `Mutex<HashMap<u64, Sender<LoopbackHandshake>>>`) as a virtual routing plane
- **`std::sync::mpsc` channel pairs** for bidirectional message flow between connections
- A **`Drop` implementation** to auto-unregister addresses from the switch when a transport is dropped

The switch maps `CandidateAddress::Memory(id)` → a handshake channel where `dial` deposits new connection endpoints and `accept` retrieves them.

The `Session` type is deliberately independent of any transport specifics. It holds:
- A monotonically increasing `session_id` (via `AtomicU64`)
- The two authoritative `PeerId`s (local and remote)
- The wrapped `Box<dyn Connection>`

This preserves the `Connection ≠ Session` distinction: the same peer identities and session ID could, in a future phase, migrate across a new connection (e.g., after a path failover) without disturbing conversational state.

#### Integration Test
`tests/integration_test.rs::test_phase1_e2e_integration_pipeline` orchestrates the full Phase 1 flow:

1. **S1.1** — Generate two `PeerId`s (Alice, Bob).
2. **S1.2** — Allocate two `CandidateAddress::Memory` locations.
3. **S1.4** — Both peers `listen()` on their loopback transports.
4. Spawn Bob's acceptor thread.
5. Alice `dial()`s Bob → obtains `LoopbackConnection`.
6. **S1.3** — Alice constructs a `ProbeStateMachine` targeting Bob, calls `on_sent()`, sends the 49-byte frame over the connection.
7. Bob's thread `accept()`s, `recv()`s, parses the `ProbeRequest`, verifies the target ID matches its own identity, constructs a `ProbeResponse`, and sends it back.
8. Alice `recv()`s the response, calls `handle_response`, asserts state is `Succeeded(rtt)`.
9. Both peers uplevel their `Connection` into a `Session` via `Session::bind`.
10. Alice sends an application frame through the session; Bob echoes an acknowledgment; both are verified.

**This test passes.** It is the single most important artifact of Phase 1: the architectural boundaries actually compose end-to-end.

#### Testing
- 1 unit test for `LoopbackTransport` bidirectional message flow
- 1 integration test for the full end-to-end pipeline
- All 18 prior tests (S1.1, S1.2, S1.3) remained green
- Final total: **20/20 passing**

#### Problems Faced & Mitigation

**Problem 1: `mpsc::Receiver` is not `Sync`.**
The `Connection` trait requires `Send + Sync` (necessary for pluggable multi-threaded transport drivers). `LoopbackConnection` held a raw `Receiver<Vec<u8>>` field, which is `Send` but not `Sync`:
```
error[E0277]: `std::sync::mpsc::Receiver<Vec<u8>>` cannot be shared between threads safely
```
**Mitigation:** Wrapped the receiver in `Mutex<Receiver<Vec<u8>>>`. This is the standard idiom: the mutex provides interior mutability with `Sync` guarantee, and `recv()` briefly locks before delegating to the underlying receiver. Alternative approaches considered:
- Using a crossbeam MPMC channel — rejected, adds a heavy dependency for a Phase 1 loopback driver
- Redesigning `Connection` to require only `Send` — rejected, would compromise future multi-threaded transports (`&Arc<dyn Connection>` shared across worker threads)

**Problem 2: Missing `Transport` trait definition after a refactor.**
During the thread-safety fix I inadvertently omitted the `pub trait Transport { ... }` block:
```
error[E0432]: unresolved import `crate::transport::Transport`
error[E0405]: cannot find trait `Transport` in this scope
```
**Mitigation:** Rewrote the file with the trait restored. Lesson: when applying a "surgical" file rewrite, verify all public items survive the transformation, not just the target of the change.

**Problem 3: Clippy `type_complexity` on the loopback channel type.**
`Sender<(CandidateAddress, Sender<Vec<u8>>, Receiver<Vec<u8>>)>` exceeded Clippy's threshold:
```
error: very complex type used. Consider factoring parts into `type` definitions
```
**Mitigation:** Introduced type aliases:
```rust
type LoopbackHandshake = (CandidateAddress, Sender<Vec<u8>>, Receiver<Vec<u8>>);
type SwitchRegistry = Mutex<HashMap<u64, Sender<LoopbackHandshake>>>;
```
This also improves the semantic readability of `dial()` and `accept()` significantly.

**Problem 4: Unused doc comment on `lazy_static!` macro.**
`///` cannot document a macro invocation:
```
error: unused doc comment
```
**Mitigation:** Downgraded the doc comment to a plain `//` comment above the macro.

**Problem 5: Unused `Arc` imports.**
Speculative imports from an earlier design draft.
**Mitigation:** Removed. The final design uses `Mutex` and `Sender`/`Receiver` cloning directly; `Arc` was not needed for the loopback path.

## 4. Architecture Discipline

### 4.1 Non-Equivalence Distinctions Preserved

The brief's Section 3 lists five protected non-equivalence pairs. Each is verified in the final code:

| Distinction | Verification |
|---|---|
| `Peer ≠ PeerId` | `PeerId` is a value type; a "Peer" is composable state across identity + addresses + sessions |
| `PeerId ≠ Address` | `PeerId` and `CandidateAddress` are separate types in separate modules |
| `Address ≠ Endpoint` | `CandidateAddress` carries no socket state; endpoints are owned by `Transport` implementations |
| `Endpoint ≠ Reachability` | `ProbeStateMachine::Succeeded(Duration)` is an empirical outcome, not an endpoint property |
| `Reachability ≠ Connection` | Probes complete before `Session::bind`; probe state and connection state are separate |
| `Connection ≠ Session` | `Session` wraps a `Box<dyn Connection>` but owns its own `session_id` and peer identities |
| `Transport ≠ Path` | Not yet exercised (Path is a Phase 2+ concept); the door is intentionally left open |

### 4.2 What Was NOT Introduced (per Section 12)

- ❌ No QUIC
- ❌ No WebRTC
- ❌ No real TCP/UDP driver
- ❌ No real Bluetooth (feature is declared but implementation is deferred)
- ❌ No mDNS or peer discovery
- ❌ No NAT traversal, ICE, or multipath scoring
- ❌ No generalized networking framework
- ❌ No Pravah coupling

### 4.3 Dependency Discipline (Section 10)

Four dependencies added, each with explicit architectural justification:

| Crate | Version | Justification |
|---|---|---|
| `ed25519-dalek` | 2.1 | Required by ADR-0002 for the cryptographic identity primitive |
| `rand` | 0.8 | Required for `OsRng` in `PeerId::random()` and 16-byte nonces in `ProbeRequest::new()` |
| `hex` | 0.4 | Required by ADR-0002 for `PeerId` human-readable encoding |
| `lazy_static` | 1.4 | Required for `LOOPBACK_SWITCH` (a `Mutex<HashMap>` needs runtime initialization) |

No speculative dependencies (no `tokio`, no `serde`, no `bytes`, no networking libraries).

## 6. Deliberate Design Observations

Two observations worth escalating for senior review:

### 6.1 The `Memory(u64)` variant is a Phase 1 pragmatism

`CandidateAddress::Memory(u64)` exists solely to make the loopback transport testable through the same abstraction as any real transport. It is architecturally clean but is not a "real" address type. If future ADRs decide that loopback should be a completely separate transport model (bypassing `CandidateAddress`), this variant can be removed. It is currently the right choice because it lets the S1.4 integration test go through the identical `dial()`/`accept()` interface a TCP driver would use.

### 6.2 `LOOPBACK_SWITCH` is a process-global singleton

The loopback switch uses `lazy_static!` for a process-wide `Mutex<HashMap>`. This is appropriate for testing and single-process demonstrations but is not a pattern to imitate for real transport drivers. Real drivers should be instantiated per-transport with explicit ownership. This is called out in ADR-0005.

Neither observation is a bug; both are conscious tradeoffs suitable for a Phase 1 research artifact.
